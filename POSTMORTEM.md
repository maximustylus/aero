# AERO — Code Post-Mortem

**Version:** 1.0 · **Date:** 2026-07-04 · **Author:** Claude (session with Alif) · **Status:** Final
**Scope:** Full repository at commit `b137c97`, plus live deployment at https://smartaero.web.app/
**Method:** Every source file read in full; git history (45 commits, all dated 2026-03-14) analysed; live site fetched; typecheck attempted. Items that could not be verified from this environment are listed in §7, not silently omitted.

---

## 1. Verdict — the most challenging work

Two areas qualify, by different measures:

1. **The deployment pipeline** was the most *struggled-with* work: 16 of 45 commits (36%) are edits to `deploy.yml`, all in a single day, classic trial-and-error debugging by pushing to `main`. It ended in a working deploy but left three conflicting Firebase identities and two live, racing deploy workflows in the repo.
2. **`CPETGame3D.tsx` (752 lines)** is the most *technically challenging* code: an imperative Three.js engine embedded in a single React effect. It works as a demo but carries a reachable soft-lock, frame-rate-dependent physics, a dead theming system, and systematic resource leaks.

Issues group into five blocks, A–E below.

---

## 2. Block A — Deployment identity crisis

### What went wrong
The repo names **three different Firebase identities** with no single source of truth:

| Artefact | Identity | Evidence |
|---|---|---|
| `deploy.yml` deploy step | `--project smartaero` | line 38 |
| `deploy.yml` service account | `github-actions-deploy@smart-aero.iam.gserviceaccount.com` (implies project id `smart-aero`) | line 23 |
| `firebase.json` | `"site": "smart-aero"` | line 3 |
| `.firebaserc` | `"default": "smartaerosim"` | line 3 |
| `firebase-hosting-merge.yml` / `-pull-request.yml` | `projectId: smartaerosim`, secret `FIREBASE_SERVICE_ACCOUNT_SMARTAEROSIM` | auto-generated by Firebase CLI |
| Live site | `smartaero.web.app` | fetched, serving |

**Two workflows both trigger on push to `main`** (`deploy.yml` and `firebase-hosting-merge.yml`) and deploy to *different* projects. Whichever succeeds last is invisible from the repo. `firebase.json`'s `"site": "smart-aero"` is inconsistent with the live URL `smartaero.web.app` (a Hosting site named `smart-aero` serves at `smart-aero.web.app`); the currently live deploy therefore cannot be fully explained from the repo state — see §7.

### Root causes
- CI was debugged by pushing to `main` repeatedly rather than validating locally (`firebase deploy` dry-run, `act`, or a scratch branch).
- The Firebase CLI's auto-generated workflows were never reconciled with the hand-written `deploy.yml` — both were kept (a conflict "averaged" rather than resolved).
- Project renames/migrations (`smartaerosim` → `smartaero`) were applied in some files and not others.

### Near-misses
- A push to `main` can ship two different builds to two different projects; users could silently receive a stale build.
- The `FIREBASE_SERVICE_ACCOUNT_SMARTAEROSIM` secret and the `smartaerosim` project may be dead; if the *other* workflow ever breaks, deploys fail with no obvious cause.

## 3. Block B — Engine defects in `CPETGame3D.tsx`

### What went wrong
1. **Reachable soft-lock (bullet time never ends).** `triggerDecisionNode()` (line 384) sets `timeScale = 0.2` and spawns a portal row. If the player jumps as portals arrive (jump apex y≈4 vs portal y=1.5; collision radius 1.5; ~40 airborne frames vs ~28-frame collision window), all portals pass, are culled at `z > 10` (line 546), and **no code path ever exits bullet time**: `timeSinceLastPortal` only accrues when `!isBulletTime` (line 443), so no new portals spawn. The game runs at 20% speed forever.
2. **Dead theming.** The scene-construction effect closes over `isDarkMode` but has `[]` deps (line 579): background, fog, bloom and all emissive materials are frozen at the initial theme. The second effect (lines 582–588) is an empty stub whose comment admits the defect. The toggle changes only the DOM overlay.
3. **Frame-rate-dependent physics.** `clock.getDelta()` is computed (line 430) but used only for the portal timer. Gravity, jump, run speed, acceleration (`+0.0001`/frame) and `slideTimer = 40` frames are all per-frame constants — the game runs twice as fast on a 120 Hz display.
4. **Fake loading and unused assets.** `LoadingManager` loads nothing; `setTimeout(() => manager.onLoad(), 500)` (line 559) fakes completion; the progress bar can never advance. Meanwhile `public/models/{character,treadmill,bike}.glb` (660 KB) ship to production and are never loaded — the runner is a capsule primitive.
5. **Resource leaks on unmount.** Cleanup disposes only the renderer. Geometries, materials, `CanvasTexture`s (one per portal label per decision node), the composer and scene children are never disposed; GSAP tweens are not killed; the 3000 ms feedback timeout and 200 ms flash timeout fire `setUiState`/material writes after unmount.
6. **Nondeterministic UI sync.** Score reaches the HUD via `if (Math.random() < 0.1)` per frame (line 433) — a probabilistic re-render churn instead of an event- or interval-driven update.
7. **Single hard-coded question.** Every decision node asks the same question with answer `"Cardiac"` (lines 387–388). The educational core of the game is one repeated item; the biased shuffle (`sort(() => Math.random() - 0.5)`) is a lesser cousin of the same shortcut.
8. **Discarded player choices and fake vitals.** Persona and mode selections (`Screen.tsx`) call the same `onNext` and store nothing; the HUD always shows "Running (Treadmill)". HR 148, VO₂ 32.1, stage 2/3, acidosis 65% and the Summary's "45.2 ml/kg/min · 94% achieved" are hard-coded, regardless of play. Pause and skip buttons have no handlers. In a clinical education tool, unlabelled fake physiology is an integrity problem, not a cosmetic one.

### Root causes
- An imperative game engine was embedded in a single React effect without a lifecycle plan; anything reactive (theme) or disposable (GPU resources) fell through the gap.
- Generated/scaffolded code was accepted wholesale at demo quality; "renders and runs" was the only acceptance test (no delta-time, no miss-handler, no disposal audit).

### Near-misses
- React StrictMode double-mounts the effect in dev — two renderers and two `InputManager`s existed briefly on every dev load; only the (partial) cleanup prevented double-input chaos.
- `onEnd()` fires mid-`animate()`; it happens to return before `composer.render()`, avoiding a render-after-unmount crash by ordering luck rather than design.

## 4. Block C — The safety net was never connected

### What went wrong
`npm run lint` is `tsc --noEmit`, but **`@types/react` / `@types/react-dom` are not in `package.json` and not installed** (verified: `node_modules/@types/` has no react; `react@19` ships no bundled `.d.ts`). Under `"strict": true` the typecheck cannot pass — it has been broken since the scripts were written. CI (`deploy.yml`) runs only `npm install && npm run build`; Vite/esbuild strips types without checking them. Net effect: **nothing has ever typechecked this codebase**, while the presence of a `lint` script and `strict: true` gave the appearance of rigour.

### Root cause
The scaffold's tsconfig promised strictness that the dependency set couldn't deliver, and no gate (CI or habit) ever executed the script that would have said so on day one.

### Near-miss
Any type error introduced in future edits ships to production silently. This block is remediated *first among code changes* because it protects every subsequent fix.

## 5. Block D — Scaffold residue

### What went wrong
- **Unused dependencies (6):** `@google/genai`, `express`, `dotenv`, `motion`, `lucide-react` (verified zero imports in `src/`), plus devDeps `@types/express`, `tsx` with no server or script to serve.
- **Secret-injection vector:** `vite.config.ts` defines `process.env.GEMINI_API_KEY` into the client bundle. No code reads it today, but if that env var ever exists at build time, the key is published to every visitor. A loaded gun pointed at a future build.
- **Dead code:** `CPETGame.tsx` (301 lines, 2-D canvas prototype) is imported nowhere.
- **Dead payload:** 660 KB of `.glb` models deployed but never fetched (Block B §4).
- **Identity residue:** package name `react-example`, AI Studio `metadata.json`, committed `.DS_Store` files, remote `lh3.googleusercontent.com` signed-URL images (landing background, avatar, hex pattern) that can expire and silently blank the UI.

### Root cause
The AI Studio scaffold was adopted without an inventory pass; nothing was ever deleted, only added.

## 6. Block E — Documentation describes a product that does not exist

### What went wrong
- **README** claims a Firebase backend — Auth (Google Sign-In), Firestore XP/session logs, Cloud Storage. **None is implemented**; there is no Firebase SDK import anywhere in `src/`.
- **TECHNICAL.md** states deployment to `smartaerosim.web.app` (live site is `smartaero.web.app`), decision nodes "every 25 seconds" (code: 30 s), velocity `+0.005`/frame (code: `+0.0001`), "high-intensity PointLights" (none exist), and persona choice customising language/complexity (choice is discarded).
- **Raw LLM citation artefacts** — `[cite_start]`, `[cite: 9]` — are committed verbatim in README and TECHNICAL.md.
- **Five names for one product:** AERO, SmartAeroSim, CPET DASH (index.html/metadata), CPET Runner (header), CPX SIM (landing hero).
- **The "PWA" claim is currently false.** There is no `manifest`, no service worker, no icons; the app is a plain SPA and is not installable or offline-capable.

### Root cause
Documentation was written aspirationally — describing the intended v2 product — and never trued against the code. This is the project's most direct violation of source-over-invention: the docs are the "plausible substitute" for a codebase that says otherwise.
